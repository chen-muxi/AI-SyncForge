# 修改需求：模块二 - 异步通知机制与超时接管优化

## 1. 修改背景
当前 `submit_and_wait` 采用每 2 秒轮询数据库的机制，性能开销大且存在响应延迟。同时，由于模块三将接管 10 分钟超时的判定权，模块二需移除原有的主动熔断逻辑，防止竞态条件。

## 2. 具体修改项

### 2.1 引入内存事件通知 (FastMCP 核心)
- **实现机制**：在 `Broker` 类或全局上下文中维护一个 `dict[int, asyncio.Event]`。
- **订阅端 (`submit_and_wait`)**：
    - 任务提交后，根据 `task_id` 创建并存储一个 `asyncio.Event`。
    - 使用 `await event.wait()` 替代 `while True: sleep(2)`。
- **发布端 (`update_task_status`)**：
    - 在完成数据库写入操作后（无论是 QA 返回结果还是 Ops-Forge 提交救助报告），检查是否存在对应 `task_id` 的 Event。
    - 若存在，执行 `event.set()` 唤醒等待中的协程。
- **资源回收机制 (防止内存泄漏)**：
    - `submit_and_wait` 必须在 `try...finally` 代码块中运行。
    - 无论任务成功、失败还是超时，在 `finally` 阶段必须执行 `event_dict.pop(task_id, None)`，确保内存不膨胀。
- **跨边界唤醒协议**：
    - **原则**：任何状态更新（包括运维介入）必须通过 FastMCP 进程内部逻辑触发。
    - **实施**：若运维工具运行在独立进程/容器，它必须通过调用 Broker 提供的内部 MCP 接口来更新状态，严禁直接操作 SQLite 绕过内存事件信号。

### 2.2 超时逻辑重构
- **移除主动超时**：删除 `submit_and_wait` 中 600 秒后强制将状态置为 `fail_by_ops_intervention` 的代码逻辑。
- **设置物理死守**：为了防止极端情况下的协程泄露，可保留一个 15-20 分钟的物理超时阈值，仅作为系统最后一道防线。

## 3. 验收标准
- [ ] **性能验证**：通过日志时间戳观察，任务状态更新到 Cursor 收到返回的时间差应从秒级进入毫秒级。
- [ ] **竞态验证**：手动将任务执行时长模拟为 11 分钟，验证 `submit_and_wait` 不会主动断开，而是等待模块三处理。
