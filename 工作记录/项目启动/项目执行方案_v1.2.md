# AI-SyncForge（AI 异步工坊）项目执行方案 v1.2

## 1. 项目愿景 (Project Vision)
本方案旨在构建一个基于自定义 MCP (Model Context Protocol) 桥接服务器的自动化开发生态，实现 **Cursor (开发者)**、**Antigravity/Gemini 3 Flash (质检员)** 与 **Ops-Forge (运维员)** 之间的三方全自动、零人工干预开发闭环。

*   **全自动化**：指令下达 -> 自动编码 -> 自动测试 -> 自动修复 -> 最终汇报。
*   **资源极简**：利用 Gemini 3 Flash 的低成本进行高频质检，优化 Token 消耗结构。
*   **架构纯净**：基于 Docker 部署，逻辑本地化，确保宿主机环境安全且不受污染。
*   **局域网共享**：支持跨设备协同，包括 Windows 11 主机及局域网内其他终端。

---

## 2. 系统架构设计 (System Architecture)
系统采用“一主多从”的架构，由一个核心中转站和多个专业智能体客户端组成。

| 组件 | 角色 | 核心逻辑 | 部署方式 |
| :--- | :--- | :--- | :--- |
| **MCP Broker** | 调度中心 | 维护 SQLite 任务队列，内置极简 Python 状态监听器。 | Docker (Alpine + Python) |
| **Cursor** | 开发主体 (Dev) | 负责代码编写，通过 MCP 提交代码块并阻塞等待测试结果。 | 本地客户端 |
| **Antigravity** | 质检主体 (QA) | 轮询任务，利用 Gemini 3 Flash 执行测试并回传报告。 | SSE 连接客户端 |
| **Ops-Forge** | 被动运维 (Ops) | **事件驱动型“急救箱”**，仅在系统抛出异常任务时介入修复。 | SSE 连接客户端 |

## 3. 技术实现细节 (Technical Implementation)

### 3.1 数据层 (SQLite)
在 Docker 挂载卷中维护 `task_queue.db`，核心表结构：
*   **tasks 表**：
    *   `id`: 唯一标识
    *   `project_name`: 项目名称
    *   `code_content`: 待测代码块
    *   `test_requirement`: 测试需求描述
    *   `task_type`: 任务类型 (`dev_test` / `ops_task`)
    *   `priority`: 优先级 (INTEGER, 默认 0, 运维任务为 999)
    *   `status`: 状态 (`pending` / `testing` / `success` / `fail` / `fail_by_ops_intervention`)
    *   `report_path`: 测试报告存放路径或故障日志路径

### 3.2 核心工具集 (MCP Tools)
1.  **`submit_and_wait(code, req)`**:
    *   **调用方**：Cursor
    *   **逻辑**：将任务写入数据库 -> 注册 `asyncio.Event` -> 挂起等待信号通知 -> 质检完成触发 `set()` 后毫秒级返回。
2.  **`poll_task()`**:
    *   **调用方**：Antigravity
    *   **逻辑**：长轮询模式。若无任务则挂起连接；发现任务则下发给测试模型。
3.  **`finish_test(task_id, status, report_meta)`**:
    *   **调用方**：Antigravity
    *   **逻辑**：更新任务状态，写入报告元数据，触发 `submit_and_wait` 的阻塞释放。
4.  **`manage_env(action, params)`**:
    *   **调用方**：Ops-Forge
    *   **逻辑**：执行环境操作。**核心限制**：严禁重启 Broker 自身容器。当调用此工具时，Broker 自动将关联任务状态置为 `fail_by_ops_intervention` 并向 Cursor 发送熔断反馈。
5.  **内置健康监听 (Non-AI)**:
    *   **实现**：Broker 内部定时器。
    *   **逻辑**：`OpsManager` 协程持续扫描超时 10 分钟的任务。若触发阈值，向队列插入一条 `priority: 999` 的 `ops_task` 运维任务。实现零 Token 损耗的被动监控。

## 4. 部署与配置指南 (Deployment)

### 4.1 Docker 环境构建
使用轻量化镜像构建服务环境：
```dockerfile
# Dockerfile
FROM python:3.11-alpine
WORKDIR /app
RUN pip install fastmcp sqlite3
COPY . .
EXPOSE 8000
# 启动 SSE 模式，挂载宿主机 Docker Socket 以实现兄弟容器管理
# 运行命令参考：docker run -v /var/run/docker.sock:/var/run/docker.sock ...
CMD ["fastmcp", "run", "server.py", "--mode", "sse", "--port", "8000"]
```

### 4.2 网络安全配置 (Windows 11)
*   **防火墙规则**：在“高级安全 Windows 防火墙”中为 TCP 8000 端口配置入站规则，允许局域网流量。
*   **地址确认**：记录宿主机局域网 IP（如 `192.168.1.100`）。

### 4.3 智能体系统提示词 (System Prompts)
*   **Cursor (开发指令)**：
    > "按照方案执行。每完成一个模块，必须调用 `submit_and_wait` 工具。在工具返回结果前保持等待。若测试失败，根据返回的报告路径读取并修复，直到通过为止。"
*   **Antigravity (测试指令)**：
    > "你是质检员。请持续调用 `poll_task`。拿到任务后，在本地项目目录生成并运行测试脚本，将结果存入 `./tests/reports/`。完成后调用 `finish_test` 同步结果。"
*   **Ops-Forge (运维指令)**：
    > "你是一个平时休眠的应急响应专家。请持续调用 `poll_ops_task`。只有当拿到了系统自动抛出的 `OPS_TASK` 时，才立即分析故障原因。你可以清理测试容器、重置缓存，但严禁动 Broker 自身。修复完成后，必须调用 `manage_env` 执行修复并同步结果。"

## 5. 自动化工作流 (Workflow)
1.  **静默运行**：Broker 内部代码监控环境，Ops-Forge 处于低成本休眠状态。
2.  **开发/测试**：Cursor 与 Antigravity 正常流转。
3.  **触发熔断**：若测试容器 OOM 或超时，Broker 抛出 `OPS_TASK` 并将当前任务熔断为 `fail_by_ops_intervention`。
4.  **应急响应**：Ops-Forge 唤醒，执行 `manage_env` 清理故障现场，并回传故障分析给 Cursor。
5.  **解封重试**：Cursor 收到熔断反馈，解除阻塞，分析是否为代码资源消耗过大，调整后重新提交。
6.  **交付/收尾**：项目完成后，Ops 执行最终环境清理。

---

## 6. 方案优势总结
*   **降本增效**：通过 Gemini 3 Flash 承担高频测试压力，显著节省高级模型 Token。
*   **异构协同**：跨设备 SSE 协议支持，充分利用碎片化算力（如笔记本、平板挂机）。
*   **质量保证**：通过“开发-测试”异构模型交叉验证，消除单一模型的认知盲区。
*   **极致简化**：用户仅需定义方案与最终验收，中间过程完全自动化。
